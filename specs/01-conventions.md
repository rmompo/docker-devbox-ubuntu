# 01 - Global conventions

## Context
Several scripts and the image share names, encoding and ways of interacting with the user. It is best to fix these once.

## Reasoning
1. Scripts must find the project's resources on their own -> a common prefix lets them filter without touching foreign resources.
2. Filtering by plain `dkdb` would also match `dkdbfoo` -> filter by `dkdb-`, with the hyphen.
3. The prefix may change (it already changed twice) -> define it in a single file loaded by every script (file names carry the prefix too, see "Script names").
4. Files are used from both Linux and Windows -> everything is UTF-8 without BOM and LF; a BOM breaks `#!/bin/bash`.
5. Windows PowerShell 5.1 reads a BOM-less `.ps1` as ANSI and corrupts non-ASCII characters -> `.ps1` files are pure ASCII, so no BOM is needed and the PowerShell version does not matter.
6. The project owner wants everything in English -> documentation, scripts, prompts, messages and comments are English, which is also naturally ASCII.
7. Users must pick from lists -> a dependency-free, reusable navigable menu.

## Decision
- **Language:** English for documentation, scripts, prompts, messages and comments.
- **Prefix:** `dkdb`, defined in one common place. Image, container and user are named `dkdb-<input>`; default input value: `devbox-ubuntu`, so the image, the container and the user are `dkdb-devbox-ubuntu` by default.
- **Prompts:** the default is displayed with the prefix (`Image name [dkdb-devbox-ubuntu:0.1.0]:` for images, which also show the version that will be built or used), but the user types only the own part, without prefix or version; the script always prepends `dkdb-`. Typing the prefix yourself would produce `dkdb-dkdb-...`.
- **Length:** `dkdb-` takes 5 characters; the typed text allows up to 27 (Linux limits user names to 32).
- **Filtering:** always by `dkdb-`.
- **Encoding:** UTF-8 without BOM and LF for every file. A BOM would only be used in a `.ps1` that needs non-ASCII characters (currently none).
- **`.gitattributes`:** `* text=auto eol=lf` (replaces the initial `* text=auto`).
- **Script names:** every file under `scripts/ps1/` and `scripts/bash/` is named `dkdb-<name>` so that, once `scripts\ps1` is on the PATH, commands cannot be confused with others. File names cannot use `$DevboxPrefix`: changing the prefix also means renaming these files.
- **Repository layout:** `install/`, `scripts/docker/`, `scripts/ps1/`, `scripts/bash/`, `specs/`.
- **Version and integrity:** `manifest.json` in the repository root is the inventory of the package: `version` (the project, semantic versioning, starting at `0.1.0`: its last number goes up in every change to a listed file and its middle number in a critical change), `image` (the version of the Docker image: it changes only when `scripts/docker/Dockerfile` or `scripts/docker/entrypoint.sh` change, so a new project version never touches the images) and `files`, the version of every file the installer downloads (and of `install/dkdb-install.ps1`), and `removed`, the paths of files that earlier versions had and this one does not (renamed or deleted scripts): `dkdb-update` deletes them from the installations, `dkdb-verify` reports them as notes and the integrity check fails when a path is in both `files` and `removed`. Each listed file carries `# Version: x.y.z` in its first lines; manifest and header must match (checked by `Get-DevboxIntegrity`: existence and version; no hashes). Installed as `<root>\devbox\manifest.json`. Every `dkdb-*.ps1`, `dkdb-install.ps1`, `dkdb-uninstall.ps1`, the bash installers and the entrypoint print their own version when they start (`Show-DevboxVersion -Script $PSCommandPath` in the common file, with the project version; the bash scripts and the entrypoint show the image version, `DEVBOX_IMAGE_VERSION`, `unknown` in an older image). **A version bump never blocks the use of an existing container**: `start` and `connect` only warn about versions (image or package); only the scripts that create things (`dkdb-image-create`, `dkdb-container-create`) require a consistent package, and `dkdb-container-create` falls back to an older image with a warning. Rules for bumping versions are in `CLAUDE.md`, which is mandatory.
- **Table of colors (one meaning for each color, defined once and used by name, never a color name in a script):** in `dkdb-common.ps1` the variables `$Devbox...Color` (the standalone installers repeat the small `$Color...` table) and in `dkdb-common.sh` the variables `c_...` and `badge_...`. Messages: success green, error red, next step yellow. Sides: host path cyan (`$DevboxHostColor`), container path magenta (`$DevboxContainerColor`); cyan is used for nothing else but the selected row of a menu. Text roles: title (headings of `-Help` and `-Man`, white), section (SECTIONS of `dkdb-info` and `dkdb-version`, white), label (a PROPERTY in capitals, orange), name (a script, command, parameter or file, orange), script (a script named in a `Next:` line, white and bold: `$DevboxScriptColor` / `c_script`) and note (version line and hints, dark gray). States: `[running]` green and `[stopped]` red. Badges (reverse video): READ-ONLY and COMPATIBLE green, READ-WRITE, MUTAGEN, VOLUME-P9 and NOT-COMPATIBLE red, MUTAGEN-SYNC yellow. Mutagen sessions: active green, paused red, and the state badge (watching green, disconnected gray, scanning yellow, reconciling orange, halted or error red). Menus: the row under the pointer cyan (the one exception to cyan being the host color: it is a selection, not a path), a changed row yellow. A path of the host or of the container is always shown in its side color, in every message.
- **Message colors:** in every script (`.ps1` and `.sh`): **green** for success, that is, something was done correctly (created, deleted, started, installed, ...); **red** for warnings and errors; **yellow** for the natural next step (for example `dkdb-container-create` -> `dkdb-container-start` -> `dkdb-container-connect`). Any other message (progress, state, cancellations) keeps the default color, and the version line is dim. In PowerShell they are `Write-DevboxSuccess`, `Write-DevboxWarning` and `Write-DevboxNext` (the standalone installers define their own copies); in bash, `ok`, `warn` and `next`, which color only when the output is a terminal, except in the entrypoint, whose messages go to the container logs and are always colored (`NO_COLOR` disables them). The menu (`Select-DevboxItem`) uses the selection colors of the table below.
- **Manual:** every script also supports `-Man` (the bash scripts: the word `man`, the Linux way; a real `man` page would need `man-db` in the image). It prints, with the same colors (white titles, orange names and numbered steps, yellow next step), and exits with 0 without doing anything else: PURPOSE, REQUIREMENTS, WHAT IT DOES (numbered), WHAT IT CHANGES, WHAT IT NEVER DOES and NEXT STEP. In PowerShell it is `Show-DevboxMan` in the common file (the standalone installers carry their own copy); in bash a `manual` function.
- **Help:** every script supports `-Help` (the bash installers use the Linux forms `-h` and `--help`), with or without other parameters. It prints, and exits with 0 without doing anything else (no Docker, no menu, no checks), these sections with the same layout: NAME, DESCRIPTION, USAGE, PARAMETERS (aligned in columns, always ending with `-Help`), EXAMPLES and NOTES, wrapped to the console width (at most 110 columns) and indented by four spaces. Colors: white titles, orange names, usage and example commands, default color for the text, a dim version line first. In PowerShell it is `Show-DevboxHelp` in the common file (the standalone installers carry their own copy); in bash a `usage` function. Scripts use `[CmdletBinding(PositionalBinding = $false)]`, so PowerShell itself rejects stray arguments. The entrypoint is not run by users and has no help.
- **Width of the screen (every script):** PowerShell reads the width of the console (`Get-DevboxConsoleWidth`, `Get-DevboxTextWidth` for the help and the manual, up to 110) and `dkdb-common.ps1` defines its own `Write-Host`, which wraps a long line at the words keeping its indentation (a line written in pieces with `-NoNewline`, a short one and redirected output go through unchanged), so every message of every script fits without calling a helper; `Get-DevboxValueLines` is the rule for the values of the info and card fields (after a space, `/` or `\\`), the notes of the sections and the version table adapt like the bash ones, and the menus cut an item longer than the line with `...` (it would wrap and break the redraw). The standalone installers carry a small copy of the same helpers (`Get-InstallConsoleWidth`, the `Write-Host` wrapper). Bash: `info_width` in `dkdb-common.sh` reads the real width of the terminal (`COLUMNS`, then `stty size` through stderr, stdin or `/dev/tty`, then `tput`, 80 when unknown; `tput` alone answers 80 inside a pipe) once per run. Everything that is printed fits in it: the values of `info_field` and the messages `ok`, `bad`, `warn` and `next` (when the output is a terminal) are wrapped at the words (after a space, `/` or `\`; a text that fits on a line of its own moves down whole), the help and the manual (`show_help`, `show_manual`, `show_usage`, `show_parameter`, `wrap_text`) use at most the width of the screen, `wrap_text` breaks a word longer than the line (a path) after a `/` or `\\` instead of at the edge, `say` is the plain message wrapped like `ok` and `next`, the status of `dkdb-ntm-ssologin-ia4d.sh` uses the layout of `dkdb-info` (`status_row` over `info_field`), the lines that follow a wrapped message keep the indentation of its first one, an item of a menu longer than the line is cut with `...`, and a section note or the name column of `dkdb-version.sh` shrink on a narrow terminal. Below about 60 columns the unbreakable lines (the usage command, the badges of a container) can still overflow.
- **Interactive menus (PowerShell and bash):** a script with options shows a menu on a terminal (the bash scripts when no argument is given; with arguments they run as always). Every menu has a screen of its own: it is cleared and drawn with the version line and the path (`Mutagen sessions > dkdb-dev`), the title and a hint of the keys under it (`Up/Down: move, Enter: select, Esc: back` or `exit`). Up/Down move, Enter selects, Esc goes back to the menu before (in the first one it ends the script). When an option ends the menu comes back, with its list read again, until the user leaves; an option that printed something (information, a result, an error) ends with `Press any key (Enter, for example) to return to the menu`, so that it is read before the screen is cleared. PowerShell: `Select-DevboxItem -Clear -EscapeAction`, `Show-DevboxMenuHeader`, `Wait-DevboxKey` and `Invoke-DevboxItemMenu` (the scripts that choose one thing and act on it) in the common file; bash: `menu_header`, `select_item`, `wait_key` and `is_interactive` in `dkdb-common.sh`. Every question that a script asks (a name, a path, a `[y/N]` confirmation) is read with `Read-DevboxLine` and the prompt says `(Esc cancels)`: Esc answers No in a confirmation and cancels the whole operation in a wizard such as `dkdb-container-create` (nothing has been created yet); the standalone installers carry a small copy of the helper (`Read-InstallLine`, `Read-UninstallLine`). A name given as a parameter (`-Container`) skips the menu of the container; without a terminal the menus are not shown.
- **Next step:** every script that ends successfully prints, in yellow, a line `Next: ...` with the natural next step. A script named in it always carries its extension (`dkdb-container-start.ps1`, `bash ~/devbox/bash/dkdb-info.sh`) and is written in the Script color (white), and in **bold** too when the terminal understands ANSI (`Write-DevboxNext` / `next` do it by looking for `dkdb-<name>.ps1|sh`; PowerShell 5.1 in the classic console, a redirected output or `NO_COLOR` lose only the bold). The color is there because on many terminals bold only means "brighter", which is not seen on the yellow of the line. The flow is `dkdb-install.ps1` -> `dkdb-image-create` -> `dkdb-container-create` -> `dkdb-container-start` -> `dkdb-container-connect` -> (inside the container) `dkdb-install-claudecode.sh` or `dkdb-install-ghcopilot-cli.sh`; the other scripts point to what normally follows them. `dkdb-container-connect` shows its hint only when the container has no AI client yet. Cancellations and errors do not print one.
- **Menu:** common function `Select-DevboxItem`, navigation only: up/down arrows, Enter confirms, Esc cancels. No numbers. ASCII, no external modules.

## Consequences
- Changing the prefix means editing one line plus renaming the `dkdb-*` files and updating their references (scripts, installer file lists, docs).
- The menu needs an interactive console; it does not work without a keyboard.
