# 08 - Mutagen (optional projects sync)

## Context
On Docker Desktop with WSL2, bind mounts from `C:\` (9p) are slow for projects with many small files. Mutagen synchronizes the host folder with a copy that lives inside the container (native ext4).

## Reasoning
1. A copy in the container removes the 9p bottleneck; Mutagen replicates changes in both directions.
2. The choice is per container, not per installation -> `dkdb-container-create` asks for it with a menu.
3. Mutagen is third-party and about 100 MB -> it is optional and installed on demand: `install.ps1` runs once, while the choice is made per container in `dkdb-container-create`.
4. The agent is copied into the container by Mutagen itself (`docker cp` + `docker exec`) -> nothing is added to the image.
5. Files created by Mutagen belong to the container user -> no "dubious ownership" problem in git.
6. Sessions are created or resumed by `start` and `connect`; `stop` never touches Mutagen, and `delete` terminates only the session of the container it deletes (a leftover session cannot reach another container because it is bound to the container ID).

## Decision
- **Installation:** `dkdb-container-create` calls `Install-DevboxMutagen` (in `dkdb-common.ps1`) when Mutagen is chosen and missing: it asks `[y/N]`, downloads the release zip of `$DevboxMutagenVersion` (0.18.1, which is also the minimum accepted version: it fixed the compatibility with Docker Engine 28+), verifies it against `SHA256SUMS`, extracts it into `<root>\devbox\mutagen\` and adds that folder to the user PATH. If declined or failed, the script aborts and creates nothing. `Get-DevboxMutagenExe` finds `mutagen.exe` in the PATH or in that folder, so the other scripts do not depend on a refreshed PATH. If a Mutagen older than the minimum is found, `dkdb-container-create` aborts and creates nothing.
- **Menu in `dkdb-container-create`:** "Docker bind mount (traditional)" or "Mutagen sync", always shown.
- **Mutagen container:** no projects bind mount; environment variables `DEVBOX_SYNC=mutagen` and `DEVBOX_SYNC_PATH=<host projects path>`. The bash volume is unchanged.
- **Session:** named `<container>-<first 12 characters of the container ID>`, `two-way-safe`, `--no-ignore-vcs`, **no ignore patterns** (everything, including `.git`, is synchronized), `--symlink-mode=ignore` (repositories are cloned on Windows, so they must not depend on symlinks), file mode `0644`, directory mode `0755`, beta owner and group = the container user. Endpoints: `<host path>` (alpha) and `docker://<user>@<container ID>/home/<user>/devbox/projects` (beta). The ID, not the name, is used so that a container recreated with the same name never reuses a leftover session.
- **Daemon:** `Test-DevboxMutagenDaemon` checks it with autostart disabled (`MUTAGEN_DISABLE_AUTOSTART=1`) and `Start-DevboxMutagenDaemon` starts it only when it is stopped and then waits up to about 10 seconds for it to answer, because `mutagen daemon start` only launches the daemon in the background and returns at once (Mutagen 0.18.1 source); if it still does not answer, it prints the exit code of `daemon start` and the error of `mutagen sync list` (for example a version mismatch with another running daemon). `dkdb-mutagen-start` and `dkdb-mutagen-stop` check the state and start or stop it by hand; stopping it stops every Mutagen session of the user. Before stopping, `dkdb-mutagen-stop` flushes the sessions of the running Mutagen containers, using the same session name (`Get-DevboxSyncSessionName`).
- **Initial synchronization:** when the session is created (or `start` asks for it), the script runs `mutagen sync flush`, which blocks until the first full cycle ends; with a large folder this takes a while. The script prints `Synchronizing ...` and, in yellow, a hint to follow it from another terminal with `dkdb-mutagen-status`. When the flush fails (`Synchronization failed while waiting for flush response` means that the synchronization cycle of the session failed meanwhile; Mutagen retries by itself), the script reads the session JSON and prints its status and `lastError` (`Show-DevboxSyncFailure`); `dkdb-mutagen-status` also shows the last error, in Mutagen's own output and as a red line.
- **`dkdb-container-start`:** after `docker start`, waits for `/dev/shm/devbox-ready` (created by the entrypoint; images built before the image version support (no `DEVBOX_IMAGE_VERSION`) do not create it, so for them it waits until the user exists instead of waiting for a marker they cannot provide), makes sure the daemon is running, creates or resumes the session and flushes.
- **`dkdb-container-connect`:** for a Mutagen container, runs the same daemon check and create-or-resume step as `start` (idempotent) but flushes only when it creates the session, so a container started with plain `docker start` or Docker Desktop gets its session back without delaying every shell. The shell opens even if the sync fails, with a warning.
- **`dkdb-container-stop`:** never touches Mutagen: no flush, no pause, no daemon stop. The session stays active (and retries to reach the container) until `start` or `connect` reconnects it. Only `dkdb-mutagen-stop` stops the daemon.
- **`dkdb-container-delete`:** for a Mutagen container, after removing it terminates its session (the name is read before the removal, because it depends on the container ID). Only that session is terminated, never the daemon or other sessions, and the daemon is not started for it: if it is not running, a warning points to `dkdb-mutagen-clean`. The host folder is not touched; the container copy is lost.
- **`dkdb-mutagen-status`:** menu of the Mutagen containers; shows `mutagen sync list` for its session (state and conflicts) and a summary read from the JSON of `mutagen sync list --template '{{json .}}'` (the `json` template function and the field names of the public session model were checked in the Mutagen 0.18.1 source; it is more stable than the display text): `So far X of Y files (Z%)`, using `stagingProgress` (`receivedFiles` of `expectedFiles`) while files are transferred and the `files` of `beta` and `alpha` otherwise; it also reports `paused`, `lastError` and the number of `conflicts`. Each query is compared with the previous one of the same session (kept in the temp folder as `dkdb-mutagen-status-<session>.json`): progress (`+N files`), a new cycle, a status change, no progress (in red) or up to date. Mutagen stages the files first and puts them in place at the end of the cycle, so the counts move in jumps. If the JSON cannot be read, the summary is skipped.
- **`dkdb-mutagen-clean`:** orphan sessions are the `dkdb-` sessions that do not match the session name of any existing Mutagen container (`Get-DevboxSyncSessionName`); the script lists them (menu, with an option for all) and terminates them after a `[y/N]` confirmation. `dkdb-container-delete` already terminates the session of the container it deletes, so leftovers only appear when a container is deleted outside the scripts or while the daemon was stopped. `start`, `connect` and `stop` never terminate sessions.
- **`tools` and `bash`** are always bind mounts; only `projects` can be synchronized.
- **Mutagen is installed outside `tools`** on purpose: `tools` is mounted read/write in every container, and `mutagen.exe` runs on the host, so a container must not be able to replace it.
- **Existing containers** keep their bind mount; recreate them to use Mutagen.

## Consequences
- `.git` is synchronized because the AI client inside the container needs the repository. Mutagen's documentation recommends against it: the Git index stores inode and mtime data specific to each filesystem (full re-hash after syncing), garbage collection reorganizes objects at any time, and hooks are a code-execution vector. Mitigation: run Git operations from one side at a time, preferably inside the container.
- Symbolic links are ignored; in `portable` mode (Mutagen's default) a non-portable link would halt the synchronization.
- Mutagen halts instead of propagating the deletion or emptying of a sync root (safety mechanisms); recover with `mutagen sync resume` or `mutagen sync reset`.
- Mutagen identifies a docker endpoint by the container identifier it is given; the ID is used (not the name) so that a leftover session never reaches another container. Leftovers (container deleted outside the scripts, or daemon stopped at that moment) are removed with `dkdb-mutagen-clean`.
- Syncing everything between Windows and Linux has risks: platform-specific `node_modules` or `.venv`, slow first scan on big trees, and case-insensitive host names. If it becomes a problem, add `--ignore` patterns in `Start-DevboxSync`.
- Not documented by Mutagen and still to verify: whether sessions resume after rebooting the PC (its data is stored in `~/.mutagen`), behavior when Docker Desktop stops with the container running, and how case-only name differences between Windows and Linux are handled.
- Mutagen license: MIT plus SSPL for the code in its `sspl` folder (included in official builds since v0.17). Devbox neither bundles nor links Mutagen; it only downloads it from its official release.
- Not tested yet on Windows with Docker (this environment has neither).
